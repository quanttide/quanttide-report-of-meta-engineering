# AI 用工具之后报告缺陷的质量评估

2026-10-06 成文。读这篇的人带着一个问题：这条线上 AI 拿工具跑完之后交出的缺陷报告能不能用。**答案：不能——八条没有一条写成本仓方法要求的可代入命题，四步（来源 → 形式化 → 代入 → 判定）全停在第一步；自环与互环本来就是建模缺陷，而规则引擎里没有这条规则，AI 也没把它们写成规则，两边对此一无所知；改进尚未形成，本篇只记差距。**

## 口径从哪来

评估用的尺子全取自已有材料，本篇不新造。

方法按 `retrospective/consistency-checking-method.md`：范畴论的用处是把声明写成等式与交换图做一致性检查，检查走命题四步，且判定解决「对不对」、不解决「要不要紧、先办哪个」。这句与 `data/journal/default/2026-10-05.md` 的定调一致——贴标签、评性质不是范畴论该干的事。

分工按 `data/context/report/retrospective/human-machine-division.md`：人类给语境与裁定权，智能体做判断与翻译，规则引擎做约束与固化；它同时记了「形式化输出默认未验证」「引擎是镜子不是脑子」两条纪律。

关卡按 `data/journal/default/2026-10-06.md`：规则检查在前、人类确认在后，分析结论必须落成可机械检查的形式并带引用（哪条映射、哪次裁决、哪份输入）。这四处主文档修正本日未动手。

证据按本仓 `CONTRIBUTING.md`：判断要挂实跑输出、代码行号、提交号，挂不住的写成待定。

## 这一轮交出的八条

三份本体在 `apps/qtcloud-meta/src/cli/examples/category/`（code、work 两份由提交 `0e2633b` 加入），三份各跑一次 `category within`，合计 46 个概念、36 条边：

| 范畴 | 概念 | 边 | 范畴定律 | 结构公理 | 领域公理 | 派生 |
|:--|--:|--:|:--|:--|:--|--:|
| qtcloud-meta-cli-category | 16 | 13 | 2/2 | 0 | 3/3 | 5 |
| qtcloud-code-cli | 17 | 13 | 2/2 | 0 | 2/2 | 2 |
| qtcloud-work-cli | 13 | 10 | 2/2 | 0 | 4/4 | 9 |

八条问题的成色，按四步标：

| 条目 | 证据 | 四步走到哪 |
|:--|:--|:--|
| 环：code 的 `CodeEvidence → CodeEvidence`、work 的 `WorkOrder ↔ WorkRecord` | 实跑加读码，核到 `evidence.rs` | 只到来源 |
| 孤点：work 的 `Workspace`、`Asset`、`Material`、`Outcome` 无边 | 读码 | 只到来源 |
| 层级缺失：36 条边全是 `Has*` | 实跑加点数 | 只到来源 |
| 过程缺失：注释里有流水线，边上没有一条表示先后 | 读码 | 只到来源 |
| 平行边：`AlignResult → ApiSignature` 两条，只因两个同类型字段 | 读码 | 只到来源 |
| 公理自证：规则与实例同一次写出 | 读码加读实现 | 观察，不是命题 |
| 粒度不一：16/4、17/9、13/12 的概念与源文件比 | 读码 | 观察，不是命题 |
| 出处会漂：`source:` 是本机绝对路径，`version` 写死 | 读码 | 观察，不是命题 |

形式化、代入、判定三步，八条里一条都没走。唯一的判定——自环不是提炼写错，`Impact` 变体里确实是 `usages: Vec<CodeEvidence>`——靠的是读码，不是代入等式。八条里六条根本不依赖工具，是直接读本体文件读出来的。

层级缺失那条的点数可以复算：

```bash
cd apps/qtcloud-meta/src/cli/examples
grep -h "kind:" category/*.yaml | sed 's/.*kind: *//;s/ }//' | sort -u | grep -v '^Has' | wc -l
# 0
```

## 结构里的边被扔掉了

工具给出的态射与复合是现成的边：派生关系 5、2、9 条，可复合对 5、4、10 对，恒等与声明态射的拆分，46 个概念与 36 条边的落点。AI 的报告只从里面取了两处——work 派生清单里的两条自反关系、结构公理 0 的那句原因。派生的 9 条本可以逐条问「两条路是不是同达」，一条没问；三张映射表共 12 行，46 个概念里 30 个一条映射都没进，这是「粒度不一」最硬的现成证据，报告里也没引。

这正是 `consistency-checking-method.md` 记的那个病：只生产点，不生产边。工具当计数器用，它的复合关系就退成了数字。

## 自环与互环：两边都无知

规则侧现在能表达的只有两类。`src/category/within.rs` 的 `check_axiom` 只认 `cardinality` 的 `min: N`；`STRUCTURAL_KINDS` 只认 Subsumption、Parthood、Causation、Opposition 四类，本体的关系种类全是 `Has*`，所以结构公理恒为 0；`src/category/between/unify.rs` 的 `build_report` 只认 `true_conflict`。关于自反、无环、孤点、平行边的规则，一条都没有。

按 10-06 日志的两级关卡，这类缺陷本该由规则检查在人类确认之前拦下，而规则集是空的——缺陷规则的缺失本身就是那四处待修正之一，本日未动手。

按 10-06 日志的判断，自环与互环本来就是系统建模缺陷；程序爆炸发生在把复合表建到闭包的那一步，走的正是这类成环结构：

```text
memory allocation of 8060 bytes failed
```

把那段循环改成只建到长度 3 之后，三份本体都在 0.00 秒、约 5MB 内跑完，报告里依然没有「这里有环」这句话。这与 `human-machine-division.md` 记的「引擎不检验入口」是同一形状：纪律保证错误可见，前提是有人先写了规则。

## 对方法的理解：两处记录与这一轮的实证

10-05 日志记着，AI 需要反复提示才能理解要从问题的本质出发使用范畴论，四版才对齐；10-06 日志记着，AI 对工具和方法的理解很差，完全不理解范畴论如何帮助理解业务结构从而发现缺陷，反复纠正也不改。

这一轮的实证吻合：AI 跑完三份 `within` 和三条 `between`，交出的结果是「定律 2/2、公理全过」，绿得像答案。三次追问——「为什么爆内存」「发现了什么业务洞察」「我要理解 AI 造的东西有哪些结构性问题」——之后，八条才出来，而八条里没有一条是命题。按 `human-machine-division.md` 第三条纪律，那份绿报告当时就该默认未验证。

## 改进尚未形成

10-06 日志写着「还没有想好怎么改进」，本节不提方案，只登记挡住改进的四件事。

缺陷判据没有落点：什么算建模缺陷，没写进任何规则、任何文档，所以八条里四条只能停在观察。规则检查还没进流程：主文档四处、CLI 文档三处都是待办，本日未动手。八条观察往规则里怎么放也没定：哪些进本体的 `axioms`、哪些进结构公理目录、哪些进 between 的冲突表，都待拍板。手册边界还有一处待核：`docs/handbook/category.md` 写本体层不用范畴论、内部一致性用描述逻辑，而 `category within` 正是拿本体当范畴跑定律，两者是否冲突没有结论。

## 边界与落地
