# lau-category-theory 引入评估

决策问题：范畴分析工具换用哪个库。2026-10-05 成文：pr4xis 因许可证含非商业条款出局，改用 `lau-category-theory`，本报告记录依据、成本与风险。读者无需技术背景。

## 结论与建议

- **采用 `lau-category-theory` 0.1.0，版本锁定**，用于范畴分析（装载、公理校验、复合与派生、报告）。
- 换库的两个理由：

  1. **许可证**。pr4xis 是 CC-BY-NC-SA-4.0，含非商业条款，代码要随产品对外分发就过不了合规；`lau-category-theory` 是 MIT，它带进来的 nalgebra（Apache-2.0）与 serde 系（MIT OR Apache-2.0）也都是可商用的宽松许可。许可取自 crates.io 的**版本级**声明（2026-10-05）。
  2. **回到规格上来**。`docs/dev-guide/category/within.md` 那套方案本来就是按 lau 写的；pr4xis 只是当年的一次试验，试验已判失败（旧报告已删，存档见附录，原文在 git 历史里）。

- **本报告不构成「工具好用」的依据。** 与上一份报告同一个立场：工具内部属性的实验不构成引入依据；能不能省人力、会不会漏拦真实违规，要从现实业务问题出题才答得上。本报告只解决「用哪个库」这一条。

## 引入成本与风险

- **库极不成熟。** 0.1.0 是它唯一的版本，crates.io 下载量 28 次，仓库在 `github.com/SuperInstance/lau-category-theory`。文档覆盖率低，按官方简介写编译不过的风险真实存在——**以源码为准，能力要实测**。
- **没有界面。** 规则以代码形式存在，改规则要工程师改代码、跑测试、发版；产品经理与运营改不了它。
- **要招会 Rust 的工程师。** 配置它靠改代码，招聘与培训口径按这个来。
- **依赖面变宽。** nalgebra（线性代数）与 serde 系会一并进依赖树，CI 里要盯住版本。

## 待决事项

1. **重新设计题目来自现实业务问题的实验**——这决定本报告能否从「采用某个库」走到「值得用下去」。
2. **版本锁定与升级策略**由工程侧确认（现锁 0.1.0）。
3. **lau 0.1.0 实际能力核对**：按源码实测一遍范畴构造、公理校验与复合派生，结论回填本报告「成本与风险」一节。

## 附录：pr4xis 三次实验存档

旧报告（`decision/pr4xis.md`）已按决议删除，原文可在 git 历史里取回。以下是它记录的三次实验，保留存档：

- **实验一与实验二：拦截演示。** 题目取自 gallery 两篇文档（主数据三层归属决议、日志与档案收敛规则），把文档规则翻成检查代码，再提交两个明知会被拦的操作——运行确实拦下了（未声明归属、未对齐事件、候选视图无人类确认）。**判失败**：题目和答案都是自己出的，只证明了工具能运转。
- **实验三：盲测。** 材料取自四篇文档（主数据三层归属、文档格式归文档工程、信用与支付、本体标准属性），18 个概念、15 条明说关系；四条预测先提交入库再运行，跑完对答案。结果：该推的一条推出来了（id 属属性的两级继承），两条不该合成的一条没合成，八条自带检查零失败，四条预测全中。**判失败**：题目是「它推得对不对」这种工具内部问题，业务方要的问题一个没答。
- 三次实验的共同判词：**工具能按自设的判据答对自设的题，不等于能在现实业务里替人省力或拦住真违规。**
