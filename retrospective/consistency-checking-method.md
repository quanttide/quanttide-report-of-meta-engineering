# 从本质出发的形式化一致性检查：一次工作方法复盘

本报告总结 2026-10-05 qtcloud-work CLI 一致性检查这条线的方法与教训。过程是：档案初稿四轮迭代（贴标签 → 性质好坏清单 → 13 条检查体 → 根因演绎），成品仍被判「分析结果帮助非常有限，解决不了人类的困惑」，同日整体删除。本报告保留方法与反思——检查方法本身站得住，站不住的是产物：它没有回答读者的问题。读者无需技术背景。

## 结论：方法七条

1. 先拿到读者的困惑与他读完要做的决定，再选工具和体裁。分析产物的验收标准是「困惑解除、能行动」，不是「检查严谨」。本次读者的困惑是「这坨东西我看得懂吗、能不能用、拿它怎么办」，产物却是 13 条等式判定——严谨、可复核，不回答任何一个人提出的问题。写不出「读者的困惑是什么」就不开工。
2. 先立目的，再动工具。范畴论在这里只有一个用途：把平台自己的声明写成等式与交换图，代入代码判定一致性。目的不说破，工具自动退化成修辞——AI 被反复提示四轮才对齐到这个目的，所以这条必须开篇写死，不能默认。
3. 四步固定：来源 → 形式化 → 代入 → 判定。来源是哪句声明蕴含了这条要求；形式化是等式、交换图或唯一性条件；代入分三级标注（实跑、读码、推演）；判定只有成立、不成立、部分成立三种。
4. 命题先行，反例后找。一致性命题都是 `∀x, f(x) = g(x)` 这种全称等式，读一侧永远证不出来；先把命题写死，找反例就从碰运气变成机械动作。
5. 检查不是终点，画像才是。结果要汇成能看出形状的分组：单实现处全过、两份拷贝处全断——这个差异才是分析产出，散点的成立与否只是原料。
6. 根因必须可证伪。「AI 生产点，不生产边」启出三条当场可验的预言：每条断裂必能点名到一对从未同框的产物、无第二份拷贝处不出事、边不物化则复发。前两条当场验过，第三条留作赌注。
7. 方法的出口是把边变成点。检查不落成测试、扫描或类型，等于又写了一遍散文——散文没有失败模式，正是三个死载体之一。外物越硬越好：编译器 > 扫描 > 测试 > 散文。

## 过程：五次纠正

- 第一版：依赖图加范畴论贴标签。纠正——这是元工程的结构分析，读者是产品经理，不是接手改代码的维护者；标签不产生判定。
- 第二版：范畴词换成「性质好坏」清单。纠正——没做形式化推理，评述多、判定少，缺乏针对性。
- 第三版：13 条检查体（来源 / 形式化 / 代入 / 结论）。方向对了；再被指出要从问题的本质出发，不要平铺。
- 第四版：根因置顶，检查按三条预言分组，补业务表现影响与档案更新协议。
- 第五次（终局）：整份删除——纠正最重的一次，产物没有解除任何人的困惑，详见下节反思。

五次纠正指向同一件事：AI 需要反复提示才对齐「到底要什么」（已记当日日志）。方法第 1 条因此置顶——它本该是第一次提示就说破的。

## 对照一则：评述与判定的差别

第二版写的是「表示不唯一，两条路不一致」——一句评述，读者无法核对，三天后没人记得它具体指什么。第三版把它写成等式并代入实值：规格公式算得 `03a3ddd1-302e-50f1-ace5-d2e74b5777f4`，实现算得 `7976aabb-d5a9-577a-ae60-39baab92ed87`，而命令行打出的正是后者——一眼判死，且任何人可用同样三个输入复算。同一发现，前者不可传递，后者可复核。

这条对照只证明「判定优于评述」，不证明「判定能解惑」——删除当天的结论补上了后半句：可复核的清单仍是清单。

## 2026-10-05 设计偏差反思：档案为什么被删

1. 把手段当成了目标。任务说「用范畴论做结构分析」，被执行成「把分析做成范畴论的样子」；范畴论与一致性都只是手段，读者的困惑才是目标。目标链条断了两节，直到删除那一刻才暴露。
2. 开工前没有定义「人类的困惑」。四轮返工全在改产出物的形式，没有一轮回头问：读者读完要做什么决定？体检报告默认「指出问题 = 有帮助」，但困惑需要的是理解与决策依据，不是清单。
3. 验收标准用了研究标准，不是读者标准。我给自己定的是「严谨、可复核、有实证」；人类的验收标准是「我懂了吗、我能行动了吗」。知道 `f ≠ g` 不等于知道修不修、先修哪个、修到什么算够。
4. 体裁错配。档案是「存档备查」的体裁；读者要的是导读（这坨东西怎么读懂）与决策备忘（能不能用、先修什么、修到什么程度就能承接业务）。内容塞进了体裁，没先问体裁对不对。
5. 解药给过，却没进产物。对话里给过三步读法（命令树 → 结果信封 → 一条竖切六百行）与「看不懂」的四个成因——恰好是解「我完全不理解 AI 写的什么玩意」的；它留在聊天里，档案里一条没有。又一次手段在手边、没问目标。

一句话归档：检查没错，证据也没错，错在它们没有回答任何一个人提出的问题。删档不是方法的失败，是产物与问题脱节的必然结果。

## 边界

- 不是每条检查都出自范畴论：说明书对结构、规矩对依赖那两条是普通对账，借了同一套体例；归功时分开说，避免把方法说胖。
- 本次没有机械化证明：全部证据来自实跑与读码；要机械化得把规格写成可执行检查。
- 术语是翻译成本：「万能对象」的实质是「19 条命令全走同一出口」，向非技术读者可整段降级为白话，结论不受影响。
- 以上三条都是方法本身的限度，但删档的原因不在此——在方法第 1 条缺位。严谨不等于有帮助。

## 落地

- 三条拍板项等产品与规格定：事件要不要保定义原文、`health` 要不要进信封、改步骤名后进度保不保——定了才写成测试，检查才算闭环。
- 方法可复用的清单：凡 AI 参与实现的平台，先枚举「哪些声明本质是等式」——身份、表示、答复、接头、文档、规矩六处是本次验证过的，换仓库仍先查这六处；查之前先写读者的困惑与决定。
- 分工边界：本报告是这条线唯一的沉淀物（原档案已删）；quanttide-work 仓的代码与规格只报告、不代改。
