# 从本质出发的形式化一致性检查：一次工作方法复盘

读这类复盘的人只想知道两件事：上次为什么没用、下次怎么开工才不跑偏。2026-10-05 那天，一份四轮迭代、带实测证据的 qtcloud-work CLI 分析档案被判「分析结果帮助非常有限，解决不了人类的困惑」并删除。本复盘用一个论点回答那两个问题：**被删的分析与它诊断的平台患的是同一种病——点是可靠的，边是没人生产的。** 方法是这个论点的推论，不是并列的守则。读者无需技术背景。

## 一、平台的病：点可靠，边断裂

被删档案里最有价值的部分，是对 qtcloud-work CLI 的 13 条一致性检查，画像只有一句话：单实现、纯计算的地方 5 条全过；同一个东西存了两份的地方几乎全断。当时把根因写成「AI 生产点，不生产边」——点是单个局部自洽的产物，边是两个点之间必须成立的关系；一致性命题形如 `∀x, f(x) = g(x)`，读 f 一万遍得不到 g 的任何信息，所以两份产物只要没被放进同一个视野，就不会有人发现它们不等。这个仓库里本该承载关系的三个载体又全是死的：关系存成字段（`step_id` 存了但不校验指向）、关系写成散文（CONTRIBUTING 的规矩从真变假不会红）、关系该进门禁（三道门禁全在看点，绿度与一致性正交）。

## 二、同一个病：诊断者自己

回头看，同一句话可以重述这次分析自己的历史。档案里每条检查都是可靠的点——实跑值、行号、任何人可复算；但「产物」与「读者的问题」之间那条边从未被生产：四轮返工（贴标签 → 性质好坏清单 → 检查体 → 根因演绎）全部在修点——换体裁、换形式、换深度——没有一轮回头问「读者读完要做什么决定」。最终判词「解决不了人类的困惑」，指的正是这条没被生产的边：产物与读者从未同框，恰如规格与代码从未同框。

这不是巧合，是同一个根因的又一次发作。一个只能生产点的主体，连「诊断」都会做成点的集合——13 条互不连通的判定、7 条方法、5 条反思，堆起来还是点。删除当天那份报告初稿本身就是第 14 个检查对象：它逐条都对，没有一条回答问题。所以这次删除不是对分析内容的否定，是「点的堆积不构成回答」这件事第一次被当场演示——包括此刻之前那两版复盘，也还在演示它。

病历（五次纠正）也顺着这个论点重述：起手版错在把手段当目的（用范畴论贴标签），第二版错在用评述冒充判定，第三版终于进入形式化（命题、代入、结论）但平铺无主线，第四版补了根因与业务影响、越补越厚，终局被删。五次里四次在修形式，纠正的深度在涨，方向没变过——全在点上加压。

## 三、为什么更严谨也没用：方法的有效域

形式化检查的有效域是命题——可代入、可证伪的等式。13 条全部成功执行，没有一条失败；第二版到第三版的进步也是真的：「表示不唯一」这句评述改写成 `uuid5(命名空间, 工作区id/名字) =? uuid5(命名空间, 工作区id/名字/workflow)`，代入实值 `03a3ddd1-…` 与 `7976aabb-…`，命令行打出的正是后者——一眼判死，任何人可复算。判定确实优于评述：可传递、可复核。

但人的困惑不在命题空间里。「我看得懂吗」「这东西能不能用」「拿它怎么办」没有代入值，判定不出成立与否，只能靠理解与决定解除。于是第四版比第一版严谨十倍，照样被删——四次纠正在同一维度加压（更严谨、更有据、更成体系），而问题在正交的维度（有没有回答谁的问题）。当日日志那句「AI 需要反复提示才能理解要从问题的本质出发使用范畴论」的两层含义在这里合拢：第一层提示说的是「范畴论的目的不是修辞」，删除这一下才说出更深的一层——「分析」的目的也不是产出分析。

可复核的清单仍是清单：判定解决「对不对」，不解决「要不要紧、先办哪个、办到什么算够」。这三问才是读者带着来的东西。

## 四、处方：三条因果

原方法七条按论点收拢成三条因果，每条都以「为什么」挂回主线。

第一，为什么先写读者的困惑与决定、再选工具和体裁：读者与产物之间的边，是所有边里唯一必须主动先生产的——它不会自己出现在任何窗口里，跟规格与代码那条一样。写不出「读者的困惑是什么」就不开工；工具的目的（范畴论 = 把声明写成等式做一致性检查）必须开篇说破，不说破就退化成修辞。

第二，为什么命题先行、四步固定（来源 → 形式化 → 代入 → 判定，实跑 / 读码 / 推演三级标注）：检查只对命题有效，把问题翻成 `∀x, f(x) = g(x)` 是进入有效域的唯一门票；命题写死之后，找反例才从碰运气变成机械动作——事件表示丢字段那条，就是靠构造两条只差 `file` 的判据一跑就塌。

第三，为什么画像、可证伪的根因、把边变成点是同一件事的三步：点的集合不自动成为认识，要靠分组（单实现全过、双拷贝全断）把点连成画像，再把画像提炼成能被打脸的预言（断裂必有产物对、无拷贝处不出事、不物化则复发）；而连起来的边要留下来，只能变成可执行物——编译器 > 扫描 > 测试 > 散文，散文没有失败模式，正是本仓三个死载体的共同死法。

## 五、边界与落地

边界：不是每条检查都出自范畴论（说明书对结构、规矩对依赖那两条是普通对账，归功分开说）；本次没有机械化证明，证据全靠实跑与读码；术语是翻译成本，「万能对象」可整段降为白话。还有一条给本报告自己：写完必须用第一节的两个问题自查——这一版回答「上次为什么没用、下次怎么开工」了吗，答不上就还是点的堆积。

落地：三条拍板项等产品与规格定（事件保不保原文、`health` 进不进信封、改步骤名后进度保不保），定了才写成测试，检查才算闭环；方法可复用的清单是六处声明（身份、表示、答复、接头、文档、规矩），查之前先写读者的困惑与决定；分工边界不变——本报告是这条线唯一的沉淀物（原档案已删），quanttide-work 仓的代码与规格只报告、不代改。
