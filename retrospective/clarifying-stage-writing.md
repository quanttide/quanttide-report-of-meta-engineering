# 澄清阶段的文档写作复盘：这轮对话里踩过的坑

读这类复盘的人只想知道两件事：澄清阶段写文档最容易在哪翻车，下次动笔照哪几条办。2026-10-06 这一轮，qtcloud-meta 的 CLI 文档从零写到分篇、再删到只剩总览，中间被逐条纠正——代拟规则、把设计稿写成契约、同一页自相矛盾。**一句话：澄清阶段的文档最怕的不是写错，是写得太像定稿——语气、结构与引用都提前进入「已定」状态，而内容一行都还没被拍板。**

## 一、五次翻车，原文与提交都在

第一，代拟规则。用户只给了立场——「范畴的性质分析要遵循一定的规则，而不是 LLM 瞎猜」——我接着写出「规则只有三样」「翻译每一步都要能追到一条具体规则」「追不到就停，宁可不给结论」，还配了一整节「为什么按规则而不靠猜」的论证。判词是「移除所有瞎编的分析规则」，全删（提交 `f3b9e05`）。立场是用户给的，细则是我编的；编完就进了正文，读起来和拍板过的没区别。

第二，语气冒充状态。`api-references/index.md` 里「已实现的接口」与设计稿同页并置，退出码写成「0 表示成功，1 表示失败」的契约，`--json` 写「字段是脚本契约，只加不改」——一个从未跑起来的命令没有契约（`eab9e48`、`3aa8da4`，后在 `fe18bd3` 随命令面一起清空）。同一页上事实与打算混排，读者分不出哪句是哪类。

第三，同页自相矛盾。总览写着「数据源主要是规格；命令行只提供本体录入格式，不提供 LLM」，同一段又复述主文档的「非结构化输入 → LLM 抽取 → …」，两句在同一段打架，直到被点名「一起更新」才改（`16b5e69`）。改口径时我只改了被点名的文件，其余文件的旧口径留在原地。

第四，结构寿命长于内容。`api-references` 先是三篇（`7501bb8`），压成两篇（`919dba9`），删到一篇（`fe18bd3`）；`user-guide` 又分出三篇（`aaaf534`）。每次分篇都连带改导航句与开发指南的分工句，全靠手工同步。三轮下来，拍板的内容在减少，目录树却越来越齐整。

第五，报告里的证据是快照。`cli-naming.md` 记的「七个命令」「`--ontology` 2/7 条消费」写的是当时的个案；个案删到零之后，这些数字不再对应仓库里任何一页，要靠人提醒才补落地说明。存档不标状态，就会和它记的东西一起过期。

## 二、根因：clarifying 档没有表达约束

`stage: clarifying` 之所以要先补，是因为没有它的时候，一篇讨论稿和一篇已验收文档在排版上完全一样。由此长出三条通病。

其一，自产事实源。AI 读到自己刚写的话会引用它：设计取向被抄进复盘报告，复盘结论又被抄回文档导航，同一个说法出现三遍就像事实了。引用方向是环形的，没有一处停在「这句拍板了吗」。

其二，立场与细则没有分界。用户给的一句立场，落到文档里需要填充物，而填充最容易的地方就是规则、数字与论证——它们写起来最快，也最难被当场识破，因为形式上完全像结论。

其三，口径变更按文件不按牵连点。改一处要连改三处（总览、子篇、开发指南的分工句），我按文件名执行，漏掉的地方就留下矛盾句，等下一轮被点名才补。

## 三、处方：下次动笔先过五条

1. 先标 stage 再动笔：`clarifying` 档不写契约句（`0/1` 退出码、「只加不改」），不与「已实现」并排；未定的结论写「尚未定义，不代拟」。
2. 立场照抄、细则留空：用户给的是立场就只写立场，细则没给就不补；要补先问一句。
3. 引用只指向事实源：过程稿之间不互相当依据，引用指向主文档或已验收文档；把自己刚写的话当依据就是自产事实源。
4. 改口径先 grep 牵连点、一次改完：改完用同一个词在各篇的口径自查，不等用户点名第二个文件。
5. 分篇跟着拍板走：没拍板的内容不铺开分篇；一篇里被拍板的结论数为零时，只留一页总览。

## 四、边界与落地

与 `cli-naming.md` 的分工：那篇管命令设计（命名、参数、该不该有命令），本篇管澄清阶段的写法；两篇在表达层面有重合，重合处以本篇为准，因为 stage 元数据与事实源规则是本篇这一轮的产物。

本轮落地：`apps/qtcloud-meta/src/cli/docs/` 六篇全部标 `stage: clarifying`，`src/cli/CONTRIBUTING.md` 写明五档（澄清 / 设计 / 实施 / 验收 / 发布）与「未验收、未发布的文档不得当事实源」。

边界：样本是单次会话，处方来自一次协作的观察，不是多次统计；报告仓本身没有 stage 概念，本篇是存档稿而非待验收稿。

待拍板两件：stage 由谁推进、什么条件算推进（AI 不自行改档）；第三节五条要不要写进主仓 `AGENTS.md` 或各 CLI 仓的 `CONTRIBUTING.md`。
